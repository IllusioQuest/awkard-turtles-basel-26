# 0022: Remaining useful heat capacity for gaming placement

Status: proposed, 2026-11-21. User confirmed ranking by available capacity to absorb heat, not stored heat. T-39, featur-gaming.

Factor the existing GreedyHeatScheduler numerator into shared HeatCapacity.RemainingKwh(HeatSignal, committedRecoverableHeatKwh). Result max(0, DemandKwh + TankCapacityKwh - TankStoredKwh - commitments); finite/nonnegative validated input and finite sums. GreedyHeatScheduler reuses it with zero commitments; valid scored inputs/results unchanged. This preserves one formula instead of gaming copying it. IScheduler/IExecutor signatures unchanged. This is an hourly admission heuristic, not the T-11/T-12 LP or a forecast guarantee.

Add a separate gaming placement library and deterministic console demo. Trusted inventory supplies per-site heat signals, country, source, UTC interval start/end exactly one hour, node IDs/readiness/network eligibility/free session slots, and external commitments (EXCLUDING reservations owned by this allocator). Requested recoverable heat per session is positive kWh for the interval, explicit synthetic in demo, not measured. One synchronized coordinator stores pending/active session reservations. New allocations filter locality/readiness/network/capacity; subtract external plus all owned pending/active commitments once per site; require enough remaining heat to accommodate the request; rank by largest remaining kWh, stable site and node IDs for ties. Claim compute slot and thermal amount together. Repeat same request ID returns original claim only if immutable request identity/parameters match. Changing heat cannot relocate an existing session.

No eligible site: return explicit unavailable, no node assignment, no automatic waste-heat operation. This does not decide queue implementation. A full tank can still absorb current demand. Clock/expired/missing/invalid snapshot rejects NEW admissions. Inventory updates for one-hour intervals retain existing reservations conservatively; active session rates are treated as the same per-hour reservation until release. External commitments must not include these sessions; this is an explicit adapter contract. Existing sessions may exceed revised heat capacity, but never migrate/terminate implicitly.

The coordinator is a local in-memory reservation model, NOT a launched-game controller or HA runtime. It has no preemption/activation endpoint: launch integration must confirm observed batch release and desktop readiness before declaring a game running. It does not release on browser disconnect or controller timeout. Caller releases only after observed session termination. Restart loses state; no runtime admission API is exposed by this demo. Durable reconciliation/fencing required before a real endpoint launches games. Atomic tests cover concurrent last-slot requests, multiple nodes sharing one site, held reservations, updates, locality, invalid/expired state and saturation ties (clipped target-load ranking is insufficient).

Review: pending limited-context review. Sources: shared Scheduling.cs, JobPlacement.cs, docs/gaming.md; case hourly model docs/case/challenge.md. No new dependency or scored economic/physical scenario.

## Review and implementation
Fresh limited-context verdict: go with changes. Applied explicit AllocatableSessionSlots (external workload occupancy excluded; allocator-owned occupancy INCLUDED), strictly increasing snapshot revisions, aligned current UTC-hour intervals, and carry-forward of held per-hour heat rates. New intervals require fresh snapshots; existing sessions remain held. This is conservative hourly admission accounting, not a prediction of session duration or actual power. The external adapter must never double-count owned reservations. Invalid updates leave the previously accepted snapshot intact; it remains usable only within its valid interval.

Shared HeatCapacity helper and in-memory SessionPlacement implemented; no runtime launch endpoint is exposed. Active and pending claims both count; activation itself has no accounting difference. Launch/preemption/termination observation and restart reconciliation remain prerequisites to a real runtime API. A deterministic synthetic console demonstration exercises home/hotel/spa selection. No changes to scored parameter values or IScheduler/IExecutor signatures.
